Автосканер кандидатов под откуп у дна: многостадийная воронка
**Stage 0 ингест → 1 фильтры → 2 анти-раг → 3 фундамент/оценка → 4 зона + доступ РФ**.
Выдаёт watchlist. **Не торгует, не даёт сигналов** — только отбирает и описывает кандидатов.

## ✨ Ключевое

- **Многостадийная воронка отбора** (8 стадий): ингест → фильтры → анти-раг/honeypot → фундамент → зона → скоринг с confidence → exit-логика.
- **Интеграция 6+ бесплатных API**: CoinGecko, GeckoTerminal, DEXScreener, GoPlus, DeFiLlama, honeypot.is.
- **Anti-rug/honeypot-детекция**, композитный скоринг 0–100, риск-логика (DD-лимит), позиции в SQLite.
- **Бэктест на 215 эпизодах** (Bybit spot, 2023–2026) + selftest на 507 офлайн-проверок.
- **Zero-dependency** — только stdlib Python 3.11+, все API бесплатные.
- **В эксплуатации с 11.07.2026** — ежедневный прогон по расписанию, см. ниже.

## В эксплуатации

Работает не на демо-данных: ежедневный прогон по расписанию с **11.07.2026**.
На 03.10.2026 — **102 прогона за 82 дня**, через воронку прошло **83 тыс. токенов**
(~1000 за прогон), в watchlist в среднем доходит ~46 (от 24 до 112). Каждый прогон
пишет снимок метрик кандидата в SQLite, поэтому тренд (растёт / умирает) виден по неделям,
а не по одному замеру. В Telegram уходят карточки на действие и сводка дня — её отсутствие
в день прогона само по себе сигнал, что прогон упал.

### Stage 5 (скор) и Stage 6 (Telegram)

- **Живость (Stage 3b)** — фильтр «легит, но труп» (survivorship показал: 60% топ-200
  умерли не от скама). Разработка — из GitHub по ссылкам CoinGecko (`sources/github.py`):
  CoinGecko с 09.2026 не отдаёт `developer_data`, и до 03.10.2026 блок был пуст у всех
  монет («живость» 5/10 у 76 из 83). Репозиторий — лента `commits.atom` (≈20 последних
  коммитов, без лимита API), организация — дата последнего push через GitHub API
  (60 запросов/час без `GITHUB_TOKEN`). Сигналы free: GitHub-коммиты за 4 недели (0 = проект встал),
  число рынков + наличие CEX (прошёл чью-то due-diligence + твой выход), LP-lock
  (разблокированный пул = раг в клик), wash-ratio (объём ≫ ликвидности = накрутка).
  Мемкоин без GitHub не штрафуется — его несёт сигнал листингов. Метрики снапшотятся
  в `candidate_metrics` каждый прогон → через недели дают ТРЕНДЫ (растёт/умирает).
- **Скор** = взвешенная сумма под-баллов (зона 0.28, оценка 0.18, безопасность 0.18,
  **живость 0.16**, торгуемость 0.10, on-chain 0.10). Недостающие блоки **не занижают балл**, а режут
  `confidence` — видно, что балл предварительный. Блок, источник которого не ответил в прогоне
  ни по одной монете (on-chain при Dune 402), в знаменатель `confidence` не входит: общая дыра
  монеты не различает. Балл = приоритизация, **не сигнал входа**.
- **Сверка тикера с Bybit**: символ совпал, а цена Bybit расходится с CoinGecko больше чем на 25%
  — это другая монета под тем же тикером (флаг `bybit_ticker_mismatch`): не «Bybit spot», без
  её фандинга, без уровней Bybit в карточке.
- **Telegram**: токен/chat_id в `.env` (`TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID`), не в коде.
  ```powershell
  py -3 run.py chat-id                 # показать chat_id (после Start боту)
  py -3 run.py telegram-test           # проверить связь
  py -3 run.py scan --track all --notify   # прогон + карточки новых монет у дна
  py -3 run.py card GRAM               # карточка монеты: текст + logs/card_GRAM.png (без отправки)
  py -3 run.py card GRAM --notify --test   # прислать карточку с пометкой «🧪 ТЕСТ»
  py -3 run.py brief                   # сводка дня (без сети); --notify — отправить без звука
  ```
  Фильтр карточек — `stage6_telegram` в config.json (`min_score`, `only_zones`, `max_alerts`),
  лестница в карточке — `card_budget_usdt` / `card_steps` (5 × $10, как у пробного исполнителя:
  цены совпадают с его журналом), картинка — `charts`.

### Stage 4: зона и доступ (проверено на живых данных)

- **Зона** = совпадение сигналов из бесплатной истории цены+объёма (CoinGecko `market_chart`,
  объём — из того же ответа, 0 доп. вызовов): сжатие волатильности (recent/чистая base < порога),
  тренд за период, позиция в диапазоне, просадка от ATH, **анти-зомби** (лоу не обновлялся ≥14д —
  медленное истечение не пружина), **объём dry-up** (<0.6 = продавцы кончились, накопление).
  Пружина ≠ падающий нож: активный даунтренд классифицируется отдельно.
- **Walk-forward проверка** (`backtest/detector_study.py`, 83 монеты Bybit, 2023–2026):
  dry-up объёма улучшает форвард (win 34→37%, mean +0.3→+1.1% свинг); гейт
  «лоу не обновлялся N дней» **опровергнут** (ухудшает монотонно — долгая плоская база
  чаще зомби, свежий лоу при сжатии = живая капитуляция) → по умолчанию выключен
  (`spring_min_days_since_low: 0`), индикатор остаётся в выводе. Hodl-выход
  (+100/+300) на горизонте 365д непроверяем — нужна бычья фаза; уровни остаются «[оценка]».
- **Survivorship-поправка** (`backtest/survivorship_study.py`): все P(+100%) — ВЕРХНЯЯ
  граница (Binance отдаёт только выживших). Когорта топ-200 CMC на пике 2021 (240 монет
  без стейблов, архив CMC + текущий CoinGecko): доживает до топ-2000 CoinGecko **73%**,
  полностью исчезли 24%, −90%+ от пика **60%**, вернулись к пику лишь **2.9%**.
  Haircut ×0.73 → истинная P(+100%|пружина) ≈ **45%** (было 61%), по циклам 2021 68→50%,
  2022 52→38%, 2023-24 63→46%. Реальная ещё ниже: Binance делистит жёстче CoinGecko-2000,
  мелкие альты вне топ-200 мрут чаще. Профиль лотерейный — доход в правом хвосте.
- **Режим BTC** (`regime.py`, 1 вызов/прогон) — контекст, не блокер: пружина при бычьем BTC
  флагается `dd_in_bull_market` (эмпирика: чаще слабость к рынку, чем недооценка).
  RS к BTC — в `indicators.rs_vs_btc_pct`.
- **Доступ РФ**: `Bybit spot` (по паспорту РФ, CEX-ликвидность + фиат) или `DEX only`
  (on-chain своим кошельком). `rf_hard_gate=false` — пока помечает, не выбрасывает.
- **CoinGecko free жёстко лимитит** `market_chart` → лимит снижен до 10/мин + 5 ретраев;
  редкие 429 дают зону `?` (дожимается на следующем прогоне из кэша). Demo-ключ снимает лимит.

### Контекст рынка альтов (`regime.py`, `sources/market.py`, таблица `market_daily`)

- **История с 2017, бесплатно**: total + BTC.D (CMC data-api, фолбэк CoinGecko `/global`),
  стейблы (DeFiLlama + CoinMetrics), MVRV BTC/ETH, Fear & Greed, фандинг и OI BTC (Bybit),
  ширина рынка (% топ-150 спот-альтов Bybit над SMA200). Бэкфилл — автоматически при первом
  скане (~3 мин), дальше обновление не чаще раза в 6 ч. Вручную: `py -3 run.py market [--backfill]`.
- **Просадка альт-рынка без стейблов** (total − BTC − стейблы) заменила просадку BTC в
  множителе качества пружины (`stage4b_quality.market_dd_source=alt`, BTC — фолбэк).
- **Индекс перегрева** — 7 флагов (альты над SMA200, MVRV BTC/ETH, F&G, ширина, фандинг,
  альты vs BTC). Хоть один горит → множитель пружины ×0.75. OI BTC убран 09.10.2026: в монетах
  он растёт при падении цены и горел всё дно 2022 ([замер](docs/OI_FLAG_REPORT.md)).
- **Валидация прод-функциями** ([отчёт](docs/MARKET_REGIME_REPORT.md),
  `backtest/market_regime_study.py`, 788 пружин Binance,
  survivor-only → P — верхняя граница): прежний BTC-dd в цикле 2020-22 ранжировал
  **наоборот** (спред верх−низ −14пп); alt-dd + перегрев — +15/+44пп в обоих циклах,
  верхняя треть по множителю P(+100/365д) 67% против 25% у нижней. Пороги флагов и штрафы —
  in-sample `[оценка]`.
- **Выход**: `watch` шлёт `market_hot` (перегрев ≥ 3/7 флагов, позиция в плюсе). Сужение
  трейла 30→15% при перегреве **выключено**: на истории медиана не меняется, а mean
  +80%→+20% (режет мании 2020-21). Проверяется вперёд: к каждой авто-paper позиции
  открывается близнец `variant=B` с сужением; `report` сравнивает книги A и B, в
  Telegram-алерты близнецы не идут.

### Про Stage 3 и free-тариф DeFiLlama (проверено на живых данных)

- `/raises` и `/emissions` теперь **платные (HTTP 402)** → точные разблокировки и раунды
  инвесторов на free недоступны, помечаются `[нет данных]`. Free-прокси навеса эмиссии —
  **FDV/MC** (из CoinGecko, бесплатно).
- Поле `mcap` в бесплатном `/protocols` почти всегда `null` → медиану MC/TVL по сектору
  считаем **из своих кандидатов** (market_cap CoinGecko + TVL DeFiLlama), не из DeFiLlama.
- TVL по gecko_id — это под-модуль, а **не родительский агрегат** (напр. Aave: сумма версий
  под `parentProtocol` вне `/protocols`). TVL может быть занижен → уточнить в Stage 4.
- Матчинг: сначала по `gecko_id` (надёжно), потом fallback по тикеру. Символьный матч
  помечается `defillama_symbol_match` + `manual_review` (риск однофамильца — проверить руками).
- Порог `min_tvl_usd` ($1M): протоколы с копеечным TVL не дают MC/TVL (иначе бред вроде
  XPR TVL $7 → MC/TVL 8e6). Живой прогон поймал это на SHIB/XPR/ROSE — теперь `mc_tvl=None`.

### Stage 7–8: выходной контур (hodl-профиль)

Стратегия: откуп у дна → холд/накопление → распределение в бычьей фазе (год-два ок).
Сканер **не торгует** — ведёт позиции (ручной ввод) и алертит сигналы выхода:

1. **Инвалидация** (всегда): 2 дневных закрытия подряд ниже лоу базы входа −25% →
   «тезис сломан, выйти» (`invalidation_below_base_low_pct`, `invalidation_confirm_days`).
2. **Лестница** (циклическая): +50% → зафиксировать 1/3, +150% → ещё 1/3 (`stage8_exit.ladder`),
   остаток — под трейл.
3. **Трейлинг** (взводимый): взводится фактом дневного закрытия ≥ +60% от средней
   (защёлка `trail_armed_ts`; старый пик до докупки вниз трейл не взводит); затем откат −30%
   от максимума с взвода → «зафиксировать остаток». До взвода просадки не выбивают.
4. **Зона распределения** (информационный): разгон +30% над SMA + верх диапазона
   (или эйфория фандинга).
5. **Перегрев рынка** (информационный): индекс перегрева ≥ 3/7 флагов при позиции в плюсе.

Все уровни считаются от `entry_price` позиции. Ступени лестницы покупок одной монеты
сливаются в одну позицию через `--merge`: количество суммируется, вход — средняя,
взвешенная по количеству (комиссия 0.15%/сторону берётся в P&L от этой средней, т.е.
средняя с комиссиями = средняя × 1.0015), `base_low` остаётся от первой ступени.
Лимит размера позиции `risk_check` проверяет по всей позиции, а не по ступени.

```powershell
py -3 run.py pos add ARB --price 0.30 --qty 1000   # записать РЕАЛЬНУЮ покупку (coin_id из watchlist/БД)
py -3 run.py pos add ARB --price 0.27 --qty 500 --merge   # ступень -> одна позиция, средняя 0.29
py -3 run.py pos list                              # открытые позиции (💰 real / 📝 paper)
py -3 run.py watch --notify                        # ре-скан (1 вызов/позицию) + Telegram
py -3 run.py pos close ARB --price 0.90            # закрыть (P&L net-of-fees в журнал)
```

**Telegram-отчётность — формат «гибрид» (03.10.2026):** звук — только когда нужно что-то
сделать руками, всё остальное тихо. Первая строка каждого сообщения — суть события (её видно
в уведомлении), детали — в свёрнутом блоке (`<blockquote expandable>`), под карточками —
кнопки-ссылки «График» (TradingView по паре Bybit или DEXScreener), «Bybit», «CoinGecko».

| Сообщение | Когда | Звук | Что внутри |
|---|---|---|---|
| Карточка монеты у дна | `scan --notify`, новая монета ≥ `min_score` (mute `alert_mute_days`) | да | цена Bybit, 5 ступеней ценами, стоп («2 закрытия ниже»), цели +50/+150% от средней, картинка 180 дн. со ступенями/стопом/целями; свёрнуто: «почему у дна», риски; пометка, если открыта paper-позиция |
| Карточка сигнала выхода | `watch --notify`, новый сигнал | реальная позиция и high/medium — да; paper и информационные — нет | что сделать и сколько продать, закрытие и P&L на момент сигнала, картинка: вход, стоп, оставшиеся цели, уровень трейла |
| Сводка дня | `brief --notify`, последний шаг `daily_run` | нет | статус scan/watch/backup, рынок (фаза цикла по просадке альтов, «температура» по флагам перегрева со значениями и порогами), монеты у дна и ниже порога, позиции со стопом и ближайшей целью ценами, сигналы дня; пометка, если срез трека Q не обновился |
| Недельная сводка | `report --if-due --notify`, первый прогон недели | нет | paper-статистика, A/B выхода и стопа, книга против альтов и BTC |
| Бэкап базы | `backup --send-weekly --notify`, первый прогон недели | нет | тонкий `.gz` документом (кандидаты за 30 дн.): дата, размер, где полные копии, как восстановить |
| Сбой шага | исключение в scan/watch/brief | да | шаг и ошибка |

- **Сводка дня — замена heartbeat**: приходит в каждый прогон; нет её в день прогона — прогон
  не дошёл до конца (`logs/`), а убитый прогон присылает «⚠ прогон убит». Коды выхода всех
  шагов `daily_run` передаёт в `brief`, поэтому упавший скан или бэкап виден в первой строке
  («⚠ бэкап не сделан», «⏱ убит по таймауту: scan»), под ней — стоп-кран, ключ Bybit, мало
  места на диске; длинная сводка уходит частями, а вчерашние
  монеты не выдаются за сегодняшние. Срезу трека Q больше `refresh_after_days` — в конце сводки
  «⚠ срез трека Q от DD.MM: автообновление не прошло, трек выключится DD.MM».
- **Картинка** — Pillow (необязательная зависимость; на этой машине стоит). Нет Pillow или
  TTF-шрифта — сообщение уходит текстом, ядро остаётся на stdlib. Внешние chart-API не
  используются — уровни позиций не уходят третьей стороне.
- **Цены**: карточка новой монеты — текущая цена и дневные свечи Bybit (если тикер прошёл
  сверку цены), иначе закрытия CoinGecko. Позиции (watch, сводка) — закрытые дневные свечи
  Bybit без кэша для монет на Bybit, иначе точки CoinGecko 00:00 UTC (`scanner/closes.py`);
  у каждого закрытия своя дата, подпись — днём закрытия («закрытие 02.10»). Закрытие
  вчерашнего дня ещё не вышло (CoinGecko отстаёт; 08.10 в 07:52 UTC точки не было ни у одной
  из 45 монет) — «⚠ цена на DD.MM»; рынок старше 2 дней — «⚠ данные рынка на DD.MM».
- **«Поддержек/сопротивлений» в карточке и на картинке нет намеренно**: ступени на узлах
  профиля объёма, цели у AVWAP/SMA200/хаёв и стоп k×ATR проверены на архиве Binance с
  умершими монетами (`backtest/levels_study.py`, [отчёт](docs/LEVELS_REPORT.md), 03.10.2026)
  — ни одно не лучше прод-правил и не отличается от placebo.
- Mute (`alert_mute_days`) пишется только монетам, которые реально пришли карточкой.
- On-chain поток (Dune) берётся из кэша, только если он моложе `onchain.max_age_hours`;
  иначе запрос перезапускается, а при отказе блок пуст (старые цифры не используются).
  Перезапуск через API с текущим ключом даёт 402 — без платного плана Dune блок пуст
  (в подвале сводки: «on-chain недоступен»).
- `report --notify` — **недельная сводка форвард-теста** (без сети, из снапшотов):
  открыто/инвалидировано/уровни/трейлинги, агрегированный P&L paper и real.
  `--if-due` — только если сводки этой недели ещё не было (так её зовёт ежедневный прогон).
  Блок **«📊 Против рынка»** (`scanner/benchmark.py`): P&L книги A (без близнецов; real —
  отдельной строкой) против альтов (total×(1−BTC.D) − стейблы) и BTC на тех же окнах (вход →
  закрытие или последний снапшот), взвешено по стоимости: плюс в растущем рынке — ещё не заслуга
  отбора; отбор полезен, только если обгоняет альты (книга v1 на 03.10: +30.7% против альтов
  +36.7% и BTC +28.0%). `benchmark.archive_db` — строка архивной книги (нет файла — пропуск). По
  позициям и с контрольной корзиной (все монеты watchlist того же прогона, прокси — капа):
  `py -3 backtest/forward_vs_benchmark.py [--archive PATH]`.
- `position_snapshots` — дневная история P&L каждой позиции (пишется watch):
  сырьё для кривой капитала и анализа качества входов через месяцы.

**Paper-режим (фоновый сбор статистики, `stage7_positions.paper_auto: true`):**
сканер сам открывает виртуальные позиции ($100) по пружинам со score ≥ 70 и
confidence ≥ 0.6 (дедуп по монете, лимит 15, cooldown re-open 30д), `watch` ведёт
их наравне с реальными (📝 в алертах). В риск-бюджет paper не входит. **Paper-executor**:
paper-позиции ВИРТУАЛЬНО исполняют свои exit-сигналы (инвалидация/трейлинг закрывают,
лестница режет qty с realized P&L) — журнал мерит стратегию-с-выходами, а не buy&hold.
Реальные позиции — только алерт, исполнение вручную (`pos reduce`/`pos close`).
Через 2–3 месяца journal = собственный форвард-тест входов И выходов на живом рынке.

**A/B на paper — близнецы** (тот же вход, та же монета, `twin_of` = id позиции A; в
лимит 15, дедуп/cooldown, алерты и дайджест не входят, итог — в `report`):
- `variant=B` — трейл сужается до 15% при перегреве рынка (`paper_ab`);
- `variant=S` — инвалидация −50% вместо −25% (`paper_ab_stop`, `paper_ab_stop_pct`),
  только для монет из среза фильтра качества (трек Q или тикер + капа из свежего среза,
  см. `track_q`). На истории стоп −50% дал медиану +11.8% против
  −1.0% у лестницы с −25%, но p10 −49% (`docs/LADDER_REPORT.md`, survivorship и in-sample),
  поэтому прод-стоп не меняется, пока paper не покажет 8–12 недель. `report` пишет P&L
  книг A и S на парах, сколько раз сработал стоп у каждой и где S лучше.

**Дисциплина закрытых свечей**: exit-логика (инвалидация/HWM/зона) работает только
на ЗАКРЫТЫХ дневных свечах — последняя точка CoinGecko market_chart это live-тик,
`closes.from_coingecko` его отбрасывает (иначе внутридневной прокол ломал бы
подтверждение инвалидации «2 закрытия подряд»). watch оценивает ВСЕ закрытия новее
`positions.last_close_ts` по порядку: отставание CoinGecko, пропущенный прогон или простой
сервера не теряют ни стопа, ни уровня лестницы; закрытие до покупки (день 0) не оценивается.
Сбой одной позиции — строка «⚠ без цены», остальные считаются (код шага 2).

Идемпотентность алертов — журнал `position_events` (сигнал не дублируется). Доставка —
очередь `notify_outbox`: карточка кладётся той же транзакцией, что событие, и снимается
только после отправки (3 попытки, 429/5xx/сеть); не дошла — повтор следующим прогоном,
сводка дня пишет «⚠ не доставлено карточек выхода: N», код watch 3. Ручной `watch` без
`--notify` очередь не трогает.
Бюджет риска: `stage7_positions.capital_usdt` (0 = выкл) — предупреждения при
превышении размера позиции и worst-case просадки портфеля 30%.

Откуда дефолты `stage8_exit`:
- `backtest/ladder_study.py` (215 эпизодов «пружины», Bybit spot 2023–2026): свинг-уровни
  +30/+60 не для hodl; hold-без-правил хуже любого системного выхода (медиана −20.8%);
  глубокая просадка при **бычьем** BTC чаще зомби, чем пружина.
- `backtest/history_calibration.py` (16.07.2026, Binance 2017–2026, 692 эпизода):
  инвалидация −5% → −25% — 59–70% пружин прокалывают базу перед ростом, буфер 25% поднял
  win 31→50%; трейл 30% после +60%.
- `backtest/feature_study.py` (17.07.2026): лестница +100/+300 → +50/+150 — на раннерах
  медиана net +36% против +26%, но режет редкие 10× (среднее ниже; survivorship).
Все уровни — верхняя граница по выжившим монетам, `[оценка]`.

### Лестница покупок и продаж (`run.py ladder`, `scanner/ladder.py`)

Считает план под Bybit spot, **ордера не выставляет**. Схема — «4 ступени до пола» из
`backtest/ladder_dca_study.py` (разбор — `docs/LADDER_REPORT.md`): ступень 1 рынком,
остальные — лимитки ровно до 1.05 × уровня прод-стопа (лоу 30 закрытий −25%).
Цены округляются к `tickSize`, количество — к `basePrecision` пары, ступень ≥ `--min-order`
($10) и ≥ минимума биржи. Выводит: ступени, стоп, худший случай (выход по стопу и
60% на гэп/делистинг), цели продажи от средней, `risk_check` при `--capital`,
пометку из последнего среза `backtest/quality_screen.py`.

```powershell
py -3 run.py ladder LINK --budget 50 --capital 1000      # prod: +50%/+150% по 1/3 + трейл
py -3 run.py ladder LINK --budget 50 --sell paired       # каждая ступень на +40%
py -3 run.py ladder LINK --budget 50 --filled 2          # цели после 2 исполненных ступеней
py -3 run.py ladder LINK --budget 100 --stop-pct 50      # вариант «широкий стоп»
```

Пробовали «умные» уровни вместо процентов (стоп k×ATR, ступени на узлах объёма, цели у
сопротивлений) — не подтвердилось, см. [docs/LEVELS_REPORT.md](docs/LEVELS_REPORT.md). Побочный
результат там же: при широком стопе (`--stop-pct 50`) важнее, идёт ли нижняя ступень за стопом
(сейчас ступени строятся до пола −25%) — неубедительно, кандидат на отдельную проверку.

Исполненные ступени: `pos add SYMBOL --price P --qty Q --base-low L --merge` на каждую —
первая открывает позицию, следующие усредняют её; цели `watch` и трейл — от средней.

На VPS (Linux) — `python3 run.py scan --track all`; ежедневный прогон — ниже.

### Ежедневный запуск (Windows)

`scripts/daily_run.ps1` — `quality --refresh-if-due` → `scan` → `watch` → `report --if-due` →
`backup --send-weekly` → `brief` с `--notify`, лог в `logs/daily_*.log` (хранится 30 дней);
сбой `quality` не блокирует `scan`, `watch` идёт и при сбое `scan`, сводка дня — всегда
последней и с кодами выхода scan/watch/backup; код скрипта ≠ 0, если упал любой шаг.
Недельная сводка и копия базы уходят первым прогоном недели
(`stage6_telegram.weekly_report_weekday`, 0 = пн).
Задачу Планировщика регистрирует `scripts/register_task.ps1` (по умолчанию 10:00, `-At "08:30"`, `-NoNotify` — без Telegram):

```powershell
powershell -ExecutionPolicy Bypass -File scripts\register_task.ps1
Start-ScheduledTask -TaskName AccumulationScannerDaily        # прогнать сейчас
Unregister-ScheduledTask -TaskName AccumulationScannerDaily -Confirm:$false   # удалить
```

Задача работает, пока пользователь в системе; проспал ноутбук — стартует после пробуждения.
Без регулярного запуска paper A/B не копит выборку: сигналы у дна редки и идут пачками.

### Ежедневный запуск (VPS, Linux)

`scripts/daily_run.sh` — то же самое для Linux (`--no-notify` — без Telegram). Расписание —
таймер systemd из `scripts/systemd/` (10:00 Europe/Samara; сервер был выключен — прогон после
включения). Проект в `/opt/scanner`, `.env`/`scanner.db` переносятся вручную (не в git):

```bash
bash scripts/install_units.sh                      # юниты в /etc/systemd/system, таймеры включены
systemctl start accumulation-scanner.service      # прогнать сейчас
systemctl list-timers --all | grep scanner        # когда следующий
bash scripts/deploy.sh                            # обновить код: selftest -> ff-only -> откат при сбое
```

Обе машины сразу не запускать: один бот, общий mute и paper-позиции у каждой свои.

Защита прогона (`daily_run.sh`, `scanner/runguard.py`): один прогон за раз (`flock`
`data/daily_run.lock`: второй — пропуск, деплой ждёт этот же замок), у каждого шага свой
таймаут (скан 90 мин, остальные 5–30 мин; убитый шаг — «⏱ таймаут» в сводке, следующие
идут), состояние в `data/daily_run.state`. Прогон убит посреди шагов (таймаут юнита 4 ч,
остановка, OOM) — «⚠ прогон убит» со звуком: trap в скрипте, `OnFailure=scanner-alert.service`,
а после перезагрузки — строка «⚠ прошлый прогон оборвался» в сводке следующего прогона.
Сводка длиннее лимита Telegram (4096) уходит частями; полный диск не роняет её.

### Стоп-кран и команды из Telegram (`scanner/control.py`)

`python3 run.py halt [причина]` или `/stop [причина]` боту — исполнитель (пробный, позже демо)
не ставит лестниц и не исполняет ордеров; скан, позиции и сводки работают, сводка дня
начинается с «⛔». Снять — **только на сервере**: `python3 run.py resume` (по SSH; владельцу
уходит сообщение). `/status` — стоп-кран, последний прогон, позиции, книги исполнителя
(в консоли: `run.py control --status`). Команды принимаются только из чата
`TELEGRAM_CHAT_ID` и только от владельца (`from.id` = `TELEGRAM_OWNER_ID`, по умолчанию
= `TELEGRAM_CHAT_ID`); чужим — одно предупреждение владельцу. Опрос — таймер
`scanner-control.timer` раз в 5 минут; молчит больше часа — строка в сводке.
`run.py chat-id` читает те же getUpdates — при включённом таймере может ничего не показать.

Ключ Bybit проверяется перед каждым `sync` (`GET /v5/user/query-api`, `scanner/keycheck.py`):
только чтение, без права вывода, привязка к IP, срок (≤ 14 дн. — предупреждение). Итог —
в сводке; опасный ключ — сообщение со звуком. Ключи — только в `.env`: непустой ключ в
`config.json` не используется (предупреждение в сводке). Защита сервера —
`scripts/vps_security_check.sh` (только чтение) и `docs/VPS_SECURITY.md` (что поменять руками).

### Бэкап базы и автообновление трека Q

`scanner.db` — единственный носитель форвард-теста (задним числом его не пересчитать).
`run.py backup` (шаг `daily_run` после `report`): копия через sqlite backup API →
`PRAGMA integrity_check` → gzip → `scanner-YYYYMMDD-HHMM.db.gz`. Хранятся ярусами (секция
`backup` в config): 14 последних (`--keep`) + самая новая копия каждой из 8 последних недель и
6 месяцев. Каталог — `/opt/backups/scanner`, если есть `/opt/backups`, иначе `backups/` в
корне (вне git). Битая база в копию не попадает и старые копии не вытесняет — пустая тоже: в
`backups.json` рядом с копиями записаны строки таблиц-журналов (runs, positions, …); меньше,
чем в последней целой копии, — копия подозрительная: пишется, но старые не удаляются, в
Telegram она не уходит, код выхода 4 (в логе `backup SUSPECT: runs 21 → 0 …`). Базу уменьшил
намеренно — `run.py backup --accept-shrink`. Раз в неделю в Telegram документом без звука уходит
тонкая копия `…-tg.db.gz` — кандидаты только за 30 дней (`telegram_candidates_days`: полная
копия растёт ~0.5 МБ/день); больше 45 МБ — не шлётся, приходит предупреждение. Восстановить (в
каталоге проекта): остановить таймер, удалить журнал прерванной записи
`rm -f scanner.db-journal scanner.db-wal scanner.db-shm` (иначе SQLite «откатит» его поверх
копии и испортит её), `gunzip -c scanner-….db.gz > scanner.db`.

Срез трека Q устаревает за `max_age_days` (30). `run.py quality` показывает, какой срез
действует; `--refresh-if-due` (первый шаг `daily_run`) с `refresh_after_days` (25) пересчитывает
`data/quality_screen_live.json` (~6 мин сети, таймаут 30 мин; файл вне git — `git pull` не
конфликтует). Берётся более свежий из него и закоммиченного `backtest/quality_screen_results.json`.
Если гейт прошли меньше 10 монет (сбой источников), срез не записывается.

### Реальные позиции из Bybit (`run.py sync`, `scanner/bybit.py`, `scanner/sync.py`)

Вместо ручного `pos add`: шаг `daily_run` между `scan` и `watch` читает спот-исполнения
Bybit V5 ключом **только на чтение** и сам ведёт реальные позиции — покупка открывает позицию
или докупает в неё (средняя по количеству, как `--merge`), продажа уменьшает её с фактической
комиссией исполнения. Количество — то, что пришло на счёт (комиссия покупки на споте часто
берётся в монете). Идемпотентно по `execId` (таблица `exchange_fills`): окна запроса
перекрываются, повтор не задваивает. Первый раз — 30 дней назад (`bybit_sync.backfill_days`,
история Bybit — 2 года), дальше — с прошлого sync. После — сверка с балансом счёта: монеты,
купленные до окна синхронизации, переведённые или лежащие в Earn, — строками в лог. Ордеров
код не ставит. Нет ключа — шаг пропускается; сбой (ключ истёк, IP, подпись) — «⚠ синхронизация
с Bybit не прошла» в сводке дня, подсказка по коду ошибки — в `logs/daily_*.log`.

Ключ создаёт владелец счёта на bybit.com (API → System-generated → HMAC) и сам вписывает
в `/opt/scanner/.env` строки `BYBIT_API_KEY=` и `BYBIT_API_SECRET=`. Права — **Read-Only**,
привязка к IP сервера (ключ без IP истекает через 90 дней), аккаунт — тот, где реально
покупаются монеты. Проверка: `python3 run.py sync`. С ключом позиции Bybit руками не вносить —
задвоятся.

### Пробный исполнитель (`run.py execute --dry-run`, `scanner/executor.py`)

Шаг 2 плана автопокупки: что поставил бы автомат — **без единого ордера** (в модуле нет ни
одного POST и приватного вызова; без `--dry-run` команда выходит с кодом 2). Шаг `daily_run`
после `watch`. Берёт монеты, пришедшие сегодня карточкой (`alert_log` ∩ `watchlist.json`:
зона дна, балл ≥ 70, confidence ≥ 0.6), и ставит лестницу `plan_ladder` — 5 × $10: ступень 1
рынком, 2–5 лимитками до пола стопа; шаги цены/количества и минимумы — из `instruments-info`.
Монета идёт парно в две книги — разница между ними только в выходах:

- **R «правила»** — `stage8_exit` целиком (стоп −25% от лоу базы, +50/+150 по трети, трейл);
- **H «держать»** — только аварийный стоп −25% (`backtest/hold_stop_study.py`).

Лимитка исполнена, если low часовой свечи Bybit после постановки **строго ниже** цены (касание
не гарантирует очередь), живёт 120 дней; выходы — по закрытым дневным свечам; комиссии 0.15% /
0.1%. Виртуальный счёт книги — $1500 (`executor.capital_usdt`), до 15 монет, `risk_check`.
Журнал — таблицы `dry_positions` / `dry_orders` с детерминированным `orderLinkId` (повтор
запуска ничего не дублирует). Реальный USDT (ключ Read-Only) — только справкой в лог.

**Отсев перед покупкой** (замер 06.10.2026, `backtest/junk_filter_study.py`: 3222 пружины
Binance 2018–2026 вместе с умершими). Строгие гейты качества (топ-150 по обороту, гейт трека Q)
режут 63–89% покупок и до 88% лучших исходов, поэтому режется только почти бесплатное:

- **Нижняя четверть по обороту** — не покупать. Место — по среднему обороту за 30 закрытых
   дневных свечей среди USDT-пар Bybit spot (`scanner/liquidity.py`: Trading, без стейблов,
   фиата, обёрток, плечевых токенов и токенизированных акций xstocks; 06.10 — 370 пар), доля =
   место / число пар > 0.75. Таких монет на истории 42% умерли за 2 года, медиана −16%.
   Места считаются раз в UTC-день (≈ 380 запросов к Bybit в 6 потоков, меньше минуты) тем, кому
   они нужны первыми — карточке в `scan --notify` или `execute`; без карточек сеть не трогается.
- **Квота неликвида** — монеты вне топ-~150 (доля > 0.39: на Binance было ~400 пар, порог
   переносится долей, а не местом) занимают не больше 5 из 15 мест книги. Считается по метке
   позиции — месту на день входа. Карточки дня идут по месту, ликвидные первыми.
- **Перегрев рынка** — горит ≥ 1 флага из 7 (`market_regime.hot_flags`; «близко» не в счёт):
   новых лестниц нет (без OI, R 2023-26: медиана −21% против +10% в холодном рынке). Данных рынка нет или
   они старше 3 дней — тоже нет: вслепую исполнитель не покупает.

Фильтры действуют только на новые входы: открытые позиции, их лимитки и выходы не трогаются.
Нет данных оборота (Bybit не ответил) — нижняя четверть и квота не отсекают. Карточка в Telegram приходит
всё равно — со строкой «⚠ нижняя четверть по обороту — исполнитель не покупает (место из N
пар)» или «🔥 перегрев — исполнитель пропускает». Порядок проверок: повтор / уже в книге →
на Bybit под тикером другая монета → нет пары, ST, не Trading → цена и план лестницы →
нижняя четверть и перегрев → лимит монет, USDT, `risk_check` → квота (полная книга — обычный
отказ, не квота).

**Теневая книга.** Отсеянное фильтрами покупается виртуально по тем же правилам — та же
лестница, те же выходы R/H, парно, — но мест, денег и `risk_check` основной книги не занимает
(`shadow = 1`, ордера `shd-…`, до 30 открытых монет). Обычные отказы (лимит монет, нет на Bybit,
ST, другая монета под тикером) в тень не идут. В каждой позиции на входе записаны метки:
место по обороту, число пар, доля, оборот, горящие флаги и день данных рынка, у тени —
причина (`shadow_why`: bottom, quota, hot, nodata). Сводка дня показывает, что не куплено и
почему («не купил бы, ушло в тень: HYPER — нижняя четверть по обороту (302-е место из 370)»),
недельная — основные книги против теневых: P&L против альтов на тех же окнах, позиции, $ и
разбивку тени по причинам. Тень хуже основной — фильтры сберегают деньги; лучше — режут
прибыль. Пороги и пояснения — секция `executor` в `config.json` (`_filters_note`).

## Конфигурация — `config.json`

Все пороги — дефолты `[оценка]`, тюнятся на бэктесте. Ключевое:
- `stage1_filters.min_volume_24h_usd / min_liquidity_usd` — порог торгуемости.
- `stage1_filters.spring_min_drawdown_from_ath_pct` (70) — предфильтр «сжатой пружины».
  `spring_hard_filter=false` → пока только помечает, не выбрасывает.
- `stage2_antirug.max_buy_tax / max_sell_tax / max_top10_holders_pct` — гейт легитимности.
- `track_q` — трек монет без контракта: `enabled`, `source` (закоммиченный срез quality_screen),
  `live_source` (автообновляемый, `data/`), `refresh_after_days` (25), `max_age_days` (30),
  `max_mcap_ratio` (капа CoinGecko/CMC ≤ 3× — защита от тёзок).
  Живой срез 29.09: 34 монеты (BTC, ETH, XRP, SOL, TRX, ADA, …). Каждая — ещё 2 вызова
  CoinGecko на Stage 3b/4, скан на free-лимите дольше на несколько минут.
- Ключи API — через env: `COINGECKO_DEMO_KEY`, `GOPLUS_KEY` (не обязательны, поднимают лимиты).
  `http.rate_limits_per_min["api.coingecko.com"]` (25) рассчитан на demo-ключ; без ключа
  берётся `http.coingecko_no_key_per_min` (10). С ключом полный scan ~15–30 мин, без него
  анонимный тариф отдаёт 429 и зона у части монет остаётся «?» (балл завышается).

## Выход

- `watchlist.json` — прошедшие воронку, «пружины» вверху списка.
- `scanner.db` (SQLite) — все кандидаты каждого прогона (таблицы `runs`, `candidates`),
  включая отклонённых с причинами и флагом `manual_review`.

## Известные ограничения (уточнить в Stage 3)

- `_pick_chain` (CoinGecko) берёт сеть по приоритету реестра, а не нативную: напр. BNB
  матчится на legacy-контракт в Ethereum. Для анти-рага ок, для on-chain-метрик Stage 3 —
  предпочитать нативную сеть.
- Track A: токены без контракта на поддерживаемых сетях (BTC, нативный ETH) отсекаются на
  Stage 1 — анти-раг для них неприменим. Исключение — трек Q (см. ниже): монеты из среза
  фильтра качества. Срез обновляется сам раз в ~25 дней; не обновился — пометка в сводке дня,
  старше `track_q.max_age_days` — трек пуст.
- Solana анти-раг у GoPlus беднее EVM — помечается флагом `solana:limited_antirug`.
- Без платных on-chain API блок «умные деньги» появится в Stage 4 на free/Dune — слабее.
